## 🔴 致命（修正推奨・Step7 VM検証の前に直す）

### S-1 / M-1（セット）: forward=PowerShell・rollback=C# Registry API の非対称で原子性に穴
- **根本（M-1）**: 同じ「fDeny/NLA を書く」が2系統。
  - forward（`Enable`）: `BuildSetDwordCommand` → PowerShell（ExitCode で失敗検知）
  - rollback（`RestoreFDenyReg`/`RestoreNlaReg`）: `_registry.WriteValue`/`_registry.DeleteValue`（C# API）
- **穴（S-1）**: `RegistryService.DeleteValue`（RegistryService.cs:74-88）は失敗しても **throw せず false を返すだけ**。
  rollback 側は戻り値を検査しない（RemoteDesktopService.cs:487-504）。
- **シナリオ**: Step2 fDeny=0 成功 → Step3 FW Enable 失敗 → 逆順 rollback で `RestoreFDenyReg`。
  backup.FDenyExisted=false（=元々キー無し＝普通の OFF 初期状態）なら `DeleteValue` を呼ぶが、
  権限喪失等で削除失敗しても **無言で false** → 例外飛ばず → fDeny=0 が残る。
  FW は開いていない（Step3失敗）ので事後検証 `IsRdpEnabled(fDeny, fwTcp=false)` は false →
  **LeftExposed 判定されず「Failed（巻き戻し済み）」と誤報告**。fDeny=0 残置のまま。
- **実害評価**: のんさん単独ローカル利用＋WinKnobs が FW を制御する通常ケースでは fDeny=0 単独は到達不可（実露出ではない）。
  ただし GPO が FW を別管理する環境では実露出になりうる＋「巻き戻した」と偽る状態汚染＝🔴機能として看過不可。
- **修正案**: ロールバックの fDeny/NLA 書き込みを forward と同じ PowerShell 経由に統一（失敗を ExitCode で必ず観測）。
  最小修正なら `RestoreFDenyReg`/`RestoreNlaReg` で `WriteValue`/`DeleteValue` の失敗を throw 化。
  加えて事後検証の露出条件を「fDeny==0 単独でも要警告（FW別管理環境の fail-safe）」に拡張を検討。

### E-1: 退避JSONの部分破損（`{}` 等）を deserialize 例外で拾えず意図せぬ無効化
- `JsonSerializer.Deserialize<RemoteDesktopBackup>` は `{}` や欠落フィールドで **例外を投げず全 default(0/false)** の record を返す。
  catch（RemoteDesktopService.cs:448）に入らない。
- 結果 `*Existed=false` → 全削除/全 Disable ＝「元に戻したつもりが無効化」。安全側だが**ユーザーの実原状を破壊**し破損通知もしない。
- **修正案**: deserialize 後に妥当性検証（必須欠落検知 or 全false/0 を破損候補として注記）。
