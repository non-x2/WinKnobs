## 🔧 @plan-validator 反映（本文より優先）

1. 🔴【致命】**項目①は Boolean 不採用 → Command 型＋値単位復元**：Boolean の復元は BackupService の .reg キー削除マーカー経由＝**キーごと削除**で、PowerThrottling キーに同居する他値を巻き添えにする。SmartScreen と同じ **Command 型（ValueExisted＋DeleteValue で値だけ復元）** を採用。なお「Boolean に ValueExisted バックアップがある」という本文 §1 の記述は事実誤認（Command 型のみ）。
2. ✅【懸念解消】RegistryService.WriteValue は CreateSubKey でキー自動作成する（RegistryService.cs:46）→ §1 の「CreateKey 併用」は不要。問題は書込側でなく復元側（上記1）。
3. 🔴**夜間モードのタイムスタンプは「blob 内既存値 +1（最小増分）」**：DateTime.Now 直挿しは CDPUserSvc との逆転負け／進めすぎは公式 UI が効かなくなる副作用。採番も純粋関数化し xUnit で「既存値+1」を検証。Apply 直後に Read 検証（書いた値が読み戻せるか）＋失敗時は Base64 退避から自動ロールバック。
4. **Sysmain 状態ラベルは世代カウンタ必須**：見落とし事例 2026-06-09（fire-and-forget リフレッシュの古い値上書きレース）に直撃。v0.1.20 の `_rdpStatusLabelGeneration` と同パターンを最初から適用。
5. **Sysmain Outcome に第4分類 `ServiceNotFound`**：`Get-Service SysMain` 不在（エディション差）を AccessDenied と誤分類しない。「このPCに SysMain がありません」案内。
6. **Sysmain タイムアウト時はプロセス Kill で強制停止しない**：Stop-Service 60秒超は中途半端なサービス状態を残す → powershell プロセスは Kill するがサービス側は「再起動で確定」案内。`-Force` の依存サービス停止副作用も Description に明記。
7. **ID を `maintenance.sysmainService` に変更**（候補集の `login.` から）：BackupService の maintenance 退避ストア分離と featureKey 命名を一致させ孤児を防ぐ。候補集 v2 側も同期修正。
8. **夜間モード blob 退避は maintenance ストアに Base64 文字列で格納**（JSON ペイロード内に Base64・新ストア追加せず既存 `SaveMaintenanceOriginalIfAbsent` 流用）。
9. **HKLM 復元も要管理者で UX 一貫**：項目①の復元は既存 HandleElevationNeeded 経路（SettingDialogViewModel.cs:559-561）に乗ることを実装時に確認。

## 1. 項目①：Power Throttling 無効化（`kernel.powerThrottlingOff`）

**最も軽い。既存 SettingItem パターンそのまま。**

- レジストリ：`HKLM\SYSTEM\CurrentControlSet\Control\Power\PowerThrottling` / `PowerThrottlingOff`（DWORD）
  - **1=スロットリング無効** / 値なし or 0=既定（有効）
  - ⚠️ **キー `PowerThrottling` 自体が既定で存在しない** → 書込時にキー作成が必要（RegistryService.WriteValue の CreateSubKey 挙動を確認・なければ CreateKey 併用）
- SettingItem：
  - Category=**Kernel** / Risk=**Yellow** / RestartScope=**System**（再起動で確実反映）
  - ValueType=Boolean・UI ON＝「スロットリングを無効化」＝レジストリ 1（InvertDisplay なし）
  - RecommendedValue=中立（一律推奨しない・ノートPCはバッテリー消費増を Description に明記）
  - DefaultValue=false（既定＝スロットリング有効）
- 復元：値が存在しなかった場合は **値削除で原状**（既存 Boolean バックアップの ValueExisted パターン）
- HKLM＝**管理者権限必須**。非昇格時は既存 HKLM 項目（SmartScreen 等）と同じ AccessDenied 案内に乗る。
- 留意（Description に記載）：非公式設定・将来の Windows Update で無視される可能性／個別アプリ除外は「設定>システム>電源」の公式 UI 案内。

**工数 0.5h・テスト：xUnit（値定義の純粋部分は薄いので項目定義スモーク）＋VM で書込/復元/AccessDenied。**

## 2. 項目②：Sysmain サービス 有効/無効（`login.sysmainService`）

**Windows サービス操作は本アプリ初。MemoryCompression（v0.1.17）同型のツールメニュー方式を踏襲。**

### 方式選定（DataGrid トグル vs ツールメニュー）
- **ツールメニュー方式を採用**（メモリ圧縮の隣・有効化/無効化の2項目）。
- 理由：①Stop-Service は数秒〜数十秒かかる＝DataGrid の同期 Apply だと UI フリーズ（Busy ガード＋Task.Run の既存メニュー基盤が必要）②サービス操作は「設定値」でなく「操作」＝Maintenance 系の既存整理と一致。
- レジストリ直叩き（`Services\SysMain\Start=4`）は**不採用**：再起動まで実状態と乖離・SCM（サービス制御マネージャ）経由が正道。

### 実装（MemoryCompression 完全同型）
- 新規 `Services/SysmainHelper.cs`（純粋関数）：
  - `BuildCommand(bool enable)`：
    - 有効化：`Set-Service -Name SysMain -StartupType Automatic -ErrorAction Stop; Start-Service -Name SysMain -ErrorAction Stop`
    - 無効化：`Stop-Service -Name SysMain -Force -ErrorAction Stop; Set-Service -Name SysMain -StartupType Disabled -ErrorAction Stop`
    - 順序：無効化は Stop→Disabled（先に止める）・有効化は Automatic→Start（先に種別）
  - `BuildReadCommand()`＋`ParseStatus(output)`：`Get-Service SysMain | ... Status/StartType` 読取（状態ラベル用・任意）
  - `Classify(exitCode, output)`＝ElevationClassifier 委譲（既存3クラスと同型）＋ `SysmainOutcome { Success, AccessDenied, Failed }`
- 新規 `Services/SysmainService.cs`：powershell.exe・60秒タイムアウト・`Kill(entireProcessTree)`・小出力前提（既存同型）
- MainViewModel：`Enable/DisableSysmainCommand`＋`IsSysmainBusy`＋`await Task.Run`＋通常 Confirm（**可逆操作＝ConfirmDestructive 不使用**・メモリ圧縮と同じ判断）
- メニュー：`MenuEnableSysmain` / `MenuDisableSysmain`（AutomationId）・メモリ圧縮の隣
- Description は中立：「HDD では無効化でカクつき軽減の報告・SSD では既定 ON のままが無難」（一律推奨しない）

**工数 1h・テスト：xUnit（BuildCommand/Classify）＋VM 実トグル（Get-Service 実測・no-op 冪等・非昇格 AccessDenied）＋UIA 非破壊（tc_maintenance_sysmain・確認ダイアログ出現＋キャンセル非実行＋StartType 不変）。**

## 3. 項目③：夜間モード 強度・色温度（`desktop.nightLightStrength`）🔶最難関

### リスクの正直な整理（実装前のダメ出し）
1. **非公開フォーマット**：CloudStore のバイナリ blob（`HKCU\...\CloudStore\Store\DefaultAccount\Current\default$windows.data.bluelightreduction.settings\windows.data.bluelightreduction.settings` の `Data` 値）。色温度はケルビン値の little-endian 可変長エンコード＋**先頭にタイムスタンプ埋込**。OS ビルドで形式が揺れる報告あり。
2. **書込後の反映**：タイムスタンプを現在時刻より進めないと CloudStore 同期が古い値で上書きし戻す挙動。Connected Devices Platform Service 依存。
3. 他ツール非対応＝差別化トップだが、**壊すと夜間モード UI がグレーアウトする事例**が知られる。

### 設計（壊さないことを最優先）
- 新規 `Services/NightLightHelper.cs`（**純粋関数に全ロジック集約・xUnit 重点**）：
  - `TryParseSettings(byte[] data, out NightLightSettings)`：blob を構造検査しながら色温度（ケルビン）を抽出。**1バイトでも想定外なら false**（書込しない）。
  - `BuildPatchedSettings(byte[] original, int kelvin, long timestamp)`：**色温度フィールドだけ差し替え＋タイムスタンプ更新**・他バイトは原本維持（全再構築しない＝形式差異に強い）。
  - 範囲ガード：公式 UI と同じ **1200K〜6500K** にクランプ。
- SettingItem は **Command 型**（Choices=プリセット段階・例「6500K(弱)/5000K/4000K/2700K(強)/1200K(最強)」）：
  - Category=Desktop / Risk=**Yellow** / RestartScope=None（即時反映）／HKCU＝昇格不要
  - Read：TryParse 成功→現在値に最も近い Choice 表示／**失敗→「（読取不可・公式設定で変更してください）」表示＋Apply 拒否**（フェイルセーフ）
  - Backup：**blob 全体を Base64 で first-touch 退避**（network/maintenance と同型の専用 or 既存ストア）→ Restore は blob 丸ごと書戻し（フォーマット解釈不要＝復元は常に安全）
  - Apply 失敗・Parse 失敗時の逃げ道：`ms-settings:nightlight` を開く案内
- **ON/OFF（bluelightreductionstate 側）は触らない**：強度のみ。ON/OFF は公式 UI/アクションセンターで十分＝攻撃面を増やさない。

**工数 1.5-2.5h・テスト：xUnit（実機から採取した blob 複数サンプルで Parse/Patch ラウンドトリップ）＋実機/VM で「公式 UI の表示が追従するか」「CloudStore に戻されないか」目視。**

### 段階逃げ道（plan-validator への論点）
パース成功率が実機で不安定なら、v0.2.0 では **「読取＋表示のみ＋公式設定へのジャンプ」へ縮退**し、書込は v0.2.1 へ送る選択肢を残す。
