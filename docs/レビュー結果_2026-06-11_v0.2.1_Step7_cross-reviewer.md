## 🔴 致命（1件）

### 致命C-1：HyperVService.SetLaunchType の no-op 退避欠落で「元に戻す」が機能しない経路
**ファイル**：src/WinKnobs/Services/HyperVService.cs:62-78
**観点**：正確性（冪等／退避原子性）＋UX

現状ロジック：
```
var (current, raw) = TryParseLaunchType(readOutput);
var target = autoOn ? Auto : Off;
if (current == target) return Success;   // ② no-op：退避を作らない
var backup = new HyperVBackup(LaunchTypeExisted: current != NotConfigured, ...);
SaveMaintenanceOriginalIfAbsent(...);    // ③ first-touch
```

問題：`current == NotConfigured`（Hyper-V 未インストールの素の状態＝LaunchTypeExisted=false）で
OFF を適用するケースを考える。
- 退避は `LaunchTypeExisted=false` で保存される → 「元に戻す」は /deletevalue を実行する（正しい）。
ここは正常。**真の問題は別**：

**Other（手動設定値）から target へ変更するとき**、退避の LaunchTypeValue=raw（例 "On" など bcdedit の
別値）は `TokenPattern`（英字のみ）を通るが、**RestoreHyperV→BuildSetLaunchTypeRawCommand で
`bcdedit /set hypervisorlaunchtype On` を実行**する。bcdedit の hypervisorlaunchtype が受け付ける値は
`Auto/Off/OptOut/RepairDisable` 等の限定セットで、退避時の生 raw が無効値だと**復元が exit≠0 で失敗**し、
「元に戻す」が永久に失敗し続ける（退避は保持されるため CanRestore は true のまま）。

さらに重大なのは **no-op 早期 return（行64）が退避保存より前**にある点。
シナリオ：ユーザーが OFF 適用（退避=Auto 保存）→ 再起動せず再度 OFF を押す → `current==Off==target` で
**②no-op return（行64）**。ここまでは無害。だが **Auto に戻す適用**を挟むと、`SaveMaintenanceOriginalIfAbsent`
は IfAbsent のため**最初の退避（Auto）を上書きしない**。これは設計意図通り。

→ 実害が確定するのは **Other 値の復元**：bcdedit が受理しない raw を退避し、復元コマンドが失敗する。

**修正案**：
1. HyperVHelper.TryParseBackup と BuildSetLaunchTypeRawCommand のトークン検査を
   「bcdedit が受理する既知値のホワイトリスト（Auto/Off/OptOut/RepairDisable）」に限定する：
```csharp
private static readonly Regex TokenPattern =
    new(@"^(Auto|Off|OptOut|RepairDisable)$", RegexOptions.Compiled | RegexOptions.IgnoreCase);
```
   （現状 `^[A-Za-z]+$` は注入は防ぐが bcdedit 無効値を通す）
2. または退避時に Other を検出したら LaunchTypeValue を保存せず「Auto へ戻す」を既定復元にフォールバック。
3. RestoreHyperV の exit≠0 時、ユーザーに「自動復元できない値だったため、Hyper-V を有効（Auto）に
   戻す/手動で bcdedit 確認」の二択を提示する。

※ Z370 開発機・一般 LDPlayer 勢は Auto/Off/NotConfigured のみなので**発生確率は低い**が、
  退避の原子性＝「保存したら必ず戻せる」が崩れる点で致命に分類。

## 🟠 重要（4件）

### 重要I-1：Boost の Backup/Apply が GUID を別々に2回解決（致命1の TOCTOU を部分的に再導入）
**ファイル**：src/WinKnobs/ViewModels/MainViewModel.cs:2179, 2186
**観点**：正確性（TOCTOU）

CommandAction は Backup→Apply の順で別々に `ResolveActiveSchemeGuidOrThrow()` を呼ぶ。
Backup が解決した GUID と Apply が解決した GUID の**間で電源プランが切り替わる**と、
「プランAの値を退避→プランBへ書込」となり、退避と書込先が食い違う。
設計ドラフト致命1は「Apply 冒頭で1回解決し Read/Write/Backup を同一 GUID」を要求しているが、
CommandAction の枠組み（Backup と Apply が独立クロージャ）では1回解決が徹底されていない。

**修正案**：BoostBackup に退避時 GUID を持たせているので Restore は正しい（退避先へ戻る）。
だが Apply 単発の AC/DC 書込先がブレるのは残る。SettingItem 適用シーケンスが
「Backup() → Apply()」を1トランザクションで呼ぶなら、両クロージャが共有する
`Lazy<string>` 的なスキャン1回キャッシュ（apply セッション単位）を導入し同一 GUID を保証する。
影響度：プラン切替は稀だが「退避と別プランへ書込→Restore で別プランが変わる」混乱。

### 重要I-2：ExternalLauncherService.RunExe が WaitForExit 前に同期 ReadToEnd（パイプデッドロック）
**ファイル**：src/WinKnobs/Services/ExternalLauncherService.cs:170-172
**観点**：正確性／パフォーマンス

```csharp
var stdout = p.StandardOutput.ReadToEnd();
var stderr = p.StandardError.ReadToEnd();
p.WaitForExit();
```
stdout を全部読み切るまでブロック→その間に子プロセスが **stderr を大量出力**するとパイプバッファ
（既定 ~4KB）が埋まり子が write でブロック→stdout が EOF に達せず**相互デッドロック**。
powercfg /query の出力は小さいので実害は出にくいが、`RunNetsh`/`RunFsutil` 等の既存呼び出しも同経路で、
タイムアウトも無い（WaitForExit() は無限待ち）。HyperVService/WslService は片方を ReadToEnd する設計
（stderr 優先・WaitForExit 後）なので**非対称**。

**修正案**：stderr を `BeginErrorReadLine`/`Task` で並行読み、または HyperV 系同様
「WaitForExit(timeout) 後に ReadToEnd」に統一＋タイムアウト付与。少なくとも powercfg 系に timeout を。

### 重要I-3：Network Throttling の DeleteOrThrow が ReadValue<string> 再読でレジストリ権限差を吸えない
**ファイル**：src/WinKnobs/ViewModels/MainViewModel.cs:2067-2075
**観点**：正確性（事例ログ 2026-06-10 DeleteValue サイレント失敗の再来チェック）

DeleteOrThrow は「DeleteValue が false かつ値が残存」で throw する正しいパターン（事例ログ準拠・◎）。
ただし `_registry.ReadValue<string>` の例外（権限なしで読めない）は **RegistryService 内で握り潰され
null 返却**の可能性がある（ReadValue は try/catch で null 化する実装）。
その場合「削除失敗＋読み直しも null」＝**残存しているのに throw されずサイレント成功扱い**になりうる。
事例ログ 2026-06-10 の「bool false がエラー網をすり抜ける」の変種。

**修正案**：DeleteValue が false の時点で（残存確認の成否に関わらず）
「削除できなかった可能性」を throw するか、ReadValue を例外透過版で確認する。
現実には Restore は管理者前提なので発生確率は中。

### 重要I-4：HyperV/WSL の AccessDenied が「読取は通るが書込で失敗」を取りこぼす（非昇格すり抜け）
**ファイル**：HyperVService.cs:54-59 / WslService.cs:42-47
**観点**：エッジケース（非昇格）／UX

bcdedit /enum・Get-WindowsOptionalFeature の**読取は非昇格でも成功**することが多い。
よって読取段階では AccessDenied を検出できず、**書込（/set・Enable）で初めて失敗**する。
書込失敗時の Classify は ElevationClassifier.LooksLikeAccessDenied(output) のキーワード依存で、
PowerShell 経由 bcdedit の権限エラー文言（日本語「アクセスが拒否されました」/英語）が
キーワード辞書に含まれるかが分類精度を左右する。含まれないと **Failed 扱い**になり
「管理者で起動し直して」の的確な誘導が出ない。

**修正案**：書込系コマンドの実行前に `WindowsIdentity` の昇格判定（IsInRole Administrator）を1回行い、
非昇格なら即 AccessDenied 相当の案内（読取は許す）。ElevationClassifier 辞書に bcdedit/DISM の
権限エラー文言（exit 0x... コード含む）が網羅されているか確認。

## 🟡 軽微 / 要監視（5件）

- 軽微M-1（UX）：CoreIsolationPolicyManaged は起動時1回キャッシュ。GPO がセッション中に
  適用/解除されてもグレーアウトが追従しない。RDP 同パターンなので一貫性はあり許容、要監視。
- 軽微M-2（保守性）：HyperVService.TimeoutMs=60_000 だが、コメント・他メンテ系（WSL=300秒）と
  「再起動系メンテ」という括りで併記され紛らわしい。bcdedit は速いので 60 秒で妥当だが、
  定数名にコメントで「bcdedit は軽量ゆえ 60 秒」と明記推奨。
- 軽微M-3（正確性）：MouseAccelHelper.ToSpiArray の ParseOrDefault は `v >= 0` のみ検査。
  Threshold に異常な大値（例 999999）が入っていても素通り。SPI_SETMOUSE は許容するので実害低、要監視。
- 軽微M-4（セキュリティ）：BoostBackup/StringBackup の退避 JSON は maintenance ストア平文。
  改ざんで SchemeGuid に任意 GUID 文字列を入れられるが、powercfg の引数化（ArgumentList）で
  シェル注入は不成立。GUID 形式検証が無いので不正 GUID で powercfg がエラー停止する程度。要監視。
- 軽微M-5（UX）：Hyper-V OFF 成功文言に「コア分離 ON だと効かない」注記はあるが、
  DisableHyperV では coreIsolationOn を読んでダイアログに渡している一方、成功 Info の offNote は
  coreIsolationOn 状態に関わらず常に同じ汎用文。ON のときだけ強調する方が誤確定防止に効く。
