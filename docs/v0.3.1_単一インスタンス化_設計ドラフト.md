## 1. 背景・なぜやるか

- v0.3.0 グラフィック実機検証中に **WinKnobs が複数起動できる（同一ユーザーセッションで 2 プロセス併存）** ことを実観測（引き継ぎメモ第33版 ⏭残3）。
- WinKnobs の退避（バックアップ）は **first-touch-wins**＝「WinKnobs で初めて触る前の値を 1 度だけ退避し、RestoreAll 成功まで上書きしない」設計。これは **単一インスタンス前提**。`Services/GraphicsService.cs:25` に「単一インスタンス強制（Mutex）を持たないため、2 窓同時操作では退避取得が競合し得る（既存の Network/Maintenance 退避と同じ既知の制約）」と明記済み。
- つまり Mutex による単一インスタンス化は、**Graphics / Network / Maintenance すべての退避の正しさを支える基盤**。既知の TOCTOU（退避取得→書込の間に別窓が割り込む）リスクの主因（複数プロセス）を構造的に閉じる。

**位置づけ**：「2 重起動でバックアップ（退避）が壊れる」は公開後にユーザーが踏みやすい信頼性事故。安定性の基盤として Public 化前に潰しておく価値が高い（README ロードマップの安定性項目）。

## 2. スコープ（やること / やらないこと）

### やること
1. **二重起動の検出と抑止**：2 個目のプロセスは自分のウィンドウを出さずに終了する。
2. **既存ウィンドウの前面化**：2 個目が起動されたら、1 個目（プライマリ）のメインウィンドウを最前面＋復元（最小化なら戻す）してフォーカス。ユーザー体験＝「もう開いてるよ、こっちだよ」。
3. **テスト可能な純粋部分の分離**：同期オブジェクト名の生成ロジックを純粋関数 Helper に切り出し xUnit で検証（プロジェクト規約：ロジックは Helper、副作用は Service）。
4. プロセス内（headless）で実 OS プリミティブ（Mutex/EventWaitHandle）の往復を検証する単体テスト（デスクトップ・入力を一切使わない）。

### やらないこと（明示）
- ❌ **コマンドライン引数の転送**（2 個目で渡したファイル等を 1 個目へ送る）＝WinKnobs は引数起動を主用途にしないため不要。将来必要なら名前付きパイプで拡張（本リリース範囲外）。
- ❌ **クロスセッション単一化**（同一ユーザーが コンソール＋RDP の 2 セッションで同時起動）＝`Global\` 名前空間＋SID 埋め込みが必要で別物。観測されたバグ（同一セッション 2 プロセス）は本スコープの `Local\`（セッション内単一）で解決する。クロスセッションの HKCU 競合はレアで、既存 TODO も主張していない＝**非対象（ドキュメントに明記）**。
- ❌ GUI 起動スモーク・実機検証・UIA（在席時 or 仮想デスクトップ・別セッション）。本セッションは **build + xUnit のみ**で検証。
- ❌ csproj の version bump・commit・push（在席での GUI 起動スモーク後／のんさん承認後）。

## 3. 仕組み（OS プリミティブ）

### 3-1. 検出＝名前付き Mutex（存在ベース・所有権ベースにしない）

```csharp
_mutex = new Mutex(initiallyOwned: false, name, out bool createdNew);
// createdNew == true  → このプロセスが最初に作った = プライマリ（1 個目）
// createdNew == false → 既に存在する        = セカンダリ（2 個目以降）
```

- **所有権（WaitOne）を取らない**＝`AbandonedMutexException` を構造的に回避。プライマリがクラッシュしても、最後のハンドルが閉じれば OS が名前付き Mutex を破棄→次回起動が createdNew=true で再びプライマリになれる（自己修復）。
- プライマリは **プロセス存続中ずっと `_mutex` を保持**（Dispose しない）。Mutex オブジェクトが生きている限り名前が存在する。
- 同時起動の競合：カーネルが「createdNew=true は厳密に 1 つ」を保証（アトミック）。

### 3-2. 起こす＝名前付き EventWaitHandle（AutoReset）

- プライマリ：`new EventWaitHandle(false, EventResetMode.AutoReset, eventName, out _)` を**早期に**作成し、待機スレッド（`IsBackground=true`）を起動。シグナルを受けたら UI スレッド（Dispatcher）で MainWindow を前面化。
- セカンダリ：`EventWaitHandle.TryOpenExisting(eventName, out var h)` で開けたら `h.Set()`、開けなくても（プライマリがまだ生成前のレア窓）**握り潰して終了**（最悪、窓が前に出ないだけ＝無害）。`TryOpenExisting` で例外を出さない。
- 停止：Dispose 時に別の「停止イベント」を Set し、待機は `WaitHandle.WaitAny([activate, stop])` で抜ける。スレッドは background なのでプロセス終了もブロックしない。

### 3-3. 同期オブジェクト名（純粋関数 `SingleInstanceNames`）

- 形式：`Local\WinKnobs_{安定GUID}_{種別}`（種別＝`Mutex` / `Activate` / `Stop`）。
  - `Local\`＝現在のログオンセッション内スコープ（＝実質ユーザー単位／同一セッション内単一化）。標準権限で作成可・ACL 既定で十分（他セッションから開けない）。`Global\` の特権（SeCreateGlobalPrivilege）問題を回避。
  - 安定 GUID＝WinKnobs 固有の固定文字列。他アプリと衝突しない一意性。
- 純粋・決定的（同じ入力→同じ名前）。テスト：3 名が相互に異なる／全て `Local\` 始まり／GUID を含む／長さ ≤ 260／空白を含まない。

### 3-4. 前面化（UI スレッド・自分の窓のみ）

```csharp
// Dispatcher 上で：
var w = Application.Current?.MainWindow;
if (w == null) return;                          // 窓未生成のレア窓は無視
if (w.WindowState == WindowState.Minimized) w.WindowState = WindowState.Normal;
w.Show();                                       // 念のため
w.Activate();
w.Topmost = true; w.Topmost = false;            // 前面化の定番ナッジ
w.Focus();
```

- **自分（WinKnobs）の窓を前面化するだけ**＝のんさんの他作業を奪わない。これはユーザーが 2 個目を起動したランタイム時のみ発火。**開発セッションでは GUI を一切起動しないため発火しない**。

## 4. 配線（App.xaml.cs）

`OnStartup` の**最初**（`_host.StartAsync()` より前）に判定を差し込む：

```text
OnStartup:
  _single = new SingleInstanceManager();        // 既定名は SingleInstanceNames から
  if (!_single.TryAcquireOwnership()):           // createdNew==false = 2個目
       _single.SignalPrimaryInstance();          // 1個目を起こす（開けなければ無視）
       Shutdown();                               // 窓を出さず終了
       return;                                    // ★ host.StartAsync / window.Show をしない
  _single.StartListening(onActivateRequested);   // プライマリ：待機スレッド開始（窓は後で生成）
  await _host.StartAsync();
  …（従来どおりテーマ適用→MainWindow.Show）
OnExit:
  _single?.Dispose();                            // Mutex 解放＋待機スレッド停止
  …（従来どおり ThemeService.Dispose / host 停止）
```

- `SingleInstanceManager` は **DI コンテナに入れない**（host 起動前に動く必要があるため App の素フィールド）。テスト時はコンストラクタにテスト専用の一意名を渡せるようにして、ホスト上で実 WinKnobs が動いていても衝突しないようにする。
- セカンダリ経路で `_single` を握ったまま Shutdown → OnExit で Dispose（createdNew=false の Mutex ハンドルを閉じるだけ・プライマリの名前は壊さない）。

## 6. テスト計画（build + xUnit のみ・デスクトップ/入力不使用）

### 純粋（SingleInstanceNames）
- 3 種別名が相互に異なる。
- 全て `Local\` で始まる・安定 GUID を含む・長さ ≤ 260・空白なし。
- 決定的（複数回呼んで同一）。

### プロセス内 OS 往復（SingleInstanceManager・一意名で衝突回避）
- 同名 2 マネージャ：1 個目 `TryAcquireOwnership()==true`、2 個目 `==false`。
- イベント往復：プライマリ `StartListening` 後にセカンダリ `SignalPrimaryInstance()` → コールバックが時間内（例 2 秒タイムアウト）に発火（テストは `ManualResetEventSlim` で待つ）。
- Dispose 後：同名で新マネージャが再び `TryAcquireOwnership()==true`（名前が解放されている）。
- `SignalPrimaryInstance` をリスナ未起動の名前に対して呼んでも例外を投げない（TryOpenExisting 失敗の握り潰し）。

> いずれも UI を出さない・フォーカスを奪わない・レジストリに触れない。CI/headless で安全。

## 7. エッジケース（机上で塞ぐ／実機保留）

| # | ケース | 対処 |
|---|---|---|
| E-1 | 同時ダブル起動の競合 | カーネルが createdNew 一意保証（アトミック）。机上 OK。 |
| E-2 | プライマリ異常終了後の再起動 | 所有権を取らない存在ベース＝ハンドル全閉で OS が名前破棄→次回プライマリ化（自己修復）。 |
| E-3 | セカンダリ送信時にイベント未生成 | `TryOpenExisting` で false→握り潰して終了（窓が前に出ないだけ・無害）。プライマリは窓生成前にイベントを作るので窓は極小。 |
| E-4 | リスナがシグナル時に窓未生成 | コールバックは `MainWindow==null` で return。 |
| E-5 | Dispose 時の待機スレッド停止 | 停止イベント＋`WaitAny`＝即時離脱。スレッドは background でプロセス終了を妨げない。 |
| E-6 | クロスセッション同時起動（同一ユーザー RDP+console） | **非対象**（`Local\` のため別セッションは別インスタンス）。ドキュメント明記。将来 `Global\`+SID で別途。 |
| E-7 | 「管理者として再起動」（PrivilegeService）後の自己再起動 | 旧プロセスが Mutex を解放（OnExit Dispose）してから新プロセスが取得。順序により一瞬両立し得るが、新プロセスは createdNew=false→**自分自身を 2 個目と誤認**し即終了する恐れ。**要検討（plan-validator 重点）**：昇格再起動は単一化の例外にする必要があるか（例：環境変数/引数で「単一化スキップ」フラグ、または旧プロセス完全終了を待つ）。 |

## 8. plan-validator への論点

1. **E-7（昇格再起動との相互作用）**：`PrivilegeService.ShutdownCurrentProcess` は graceful shutdown→1500ms 後に `Environment.Exit`。runas で起動した新プロセスが旧プロセスの Mutex 解放前に立ち上がると、新プロセスが createdNew=false で**自滅**＝「管理者として再起動」したのに窓が出ない事故。対策案を要評価（a: 昇格子プロセスに `--allow-second`/環境変数を渡し単一化を一回スキップ、b: セカンダリは「既存窓を起こせなかった時だけ」終了せずリトライ、c: 旧プロセス側を `Shutdown` 完了まで待たせる）。
2. **スコープ（`Local\` セッション内単一）で十分か**＝観測バグは同一セッション 2 プロセス。クロスセッションを非対象と割り切る判断の妥当性。
3. **前面化の方法**（Topmost ナッジ）が WPF/Win11 で確実か、`SetForegroundWindow` の前景ロック制限（別プロセスからの前面化は OS が制限）に当たらないか。※同一プロセス＝プライマリ自身が自分の窓を Activate するので前景ロック制限の対象外のはず（要確認）。
4. テスト計画にプロセス内 OS 往復を含めることの妥当性（flaky にならないタイムアウト設計）。

## 🔧 plan-validator 反映（2026-06-22・@plan-validator Sonnet／本節がドラフト本文より優先）

> 致命3・重要4・エッジ4 の指摘を全件トリアージ。採用＝以下に確定仕様として記す。

### 致命

- **致命1（昇格再起動レース・Environment.Exit の1500ms窓）**：採用。
  - `PrivilegeService.TryRestartAsAdministrator` の runas 子プロセスに環境変数 `WINKNOBS_SINGLE_INSTANCE_RESTART=1` を付与（`ProcessStartInfo.EnvironmentVariables` は `UseShellExecute=true` と併用不可のため、**`UseShellExecute` は true 維持＋環境変数は `Environment.SetEnvironmentVariable` で現プロセスに一時セットしてから起動→子へ継承**…ではなく runas は新規環境で起動するため、確実なのは「親が自身の環境変数に一時セット→Process.Start で子へ継承」。runas+UseShellExecute=true でも子は親の環境ブロックを継承するため、**親プロセスで `Environment.SetEnvironmentVariable("WINKNOBS_SINGLE_INSTANCE_RESTART","1")` を Process.Start 直前に実行**する）。
  - `App.OnStartup` 冒頭で当該環境変数を読む。立っていれば `TryAcquireOwnership(waitForRelease: true)`＝旧プロセスが Mutex を解放するまで短時間（既定 ~3 秒・小刻みリトライ）待って取得を試み、**取得失敗でも自滅せず窓を出す**（昇格再起動の目的＝窓を見せること を最優先）。立っていなければ従来どおり `waitForRelease:false`。
  - これにより「管理者として再起動したのに窓が出ない」を構造的に解消。`waitForRelease` のリトライは in-process Mutex で単体テスト可能。
- **致命2（ShutdownMode と Shutdown() の競合）**：採用（別案）。
  - セカンダリ経路は `Shutdown()` を使わず **`Environment.Exit(0)`**。窓0枚でも ShutdownMode に依存せず確実終了。`PrivilegeService.ShutdownCurrentProcess` が既に `Environment.Exit(0)` を保険に使う **既存パターンに合わせる**。`ShutdownMode` はプライマリの「窓を閉じたら終了（OnLastWindowClose）」を壊さないため **変更しない**（OnExplicitShutdown 化は窓クローズで終了しなくなる回帰のため不採用）。
  - 順序：`SignalPrimaryInstance()`（Set はカーネルへ同期的にキュー）→ `Environment.Exit(0)`。
- **致命3（待機スレッド未捕捉例外でクラッシュ）**：採用。
  - 待機ループ全体を `try/catch`：`ObjectDisposedException` は正常停止扱いで break、それ以外は `Trace`＋break（プロセスを落とさない）。
  - `Dispose` 順序＝`_stopEvent.Set()` → `_listenerThread.Join(1000)`（WaitAny から確実に離脱）→ ハンドル破棄。これで「WaitAny 使用中にハンドル破棄」を回避。

### 重要

- **重要1（Topmost ナッジが子窓を沈める既知事例の横展開）**：採用。
  - 前面化＝「最小化なら Normal 復元 → `Activate()`」を基本とし、**`Application.Current.Windows.Count > 1`（子ダイアログが開いている）時は Topmost ナッジを行わない**（SettingDialog/RestorePreviewDialog/VirtualMemoryDialog 等が MainWindow 背後に沈むのを防止）。子窓が無い時だけ `Topmost=true→false` ナッジ。
- **重要2/3（テストの flaky・IDisposable リーク）**：採用。
  - テスト用同期名は各テスト冒頭で `$"Local\\WinKnobsTest_{Guid.NewGuid():N}_{種別}"` を生成しコンストラクタ注入。全マネージャを `using var` で破棄。OS 往復テストは `[Collection("SingleInstanceSerial")]` で**直列実行**（xUnit 既定の並列を無効化し相互干渉を防ぐ）。コールバック待ちタイムアウトは `Debugger.IsAttached ? 10000 : 2000` ms。
- **重要4（App フィールド宣言・OnExit null チェック）**：採用。
  - `App` に `private SingleInstanceManager? _single;` を宣言。`OnExit` の `_single?.Dispose()` は ThemeService と同じ `try/catch` で包む。OnStartup の単一化判定全体も `try/catch` し、**例外時はフェイルオープン（プライマリ扱いで窓を出す）**＝単一化は「あれば良い」機能でアプリ起動を妨げない。

### エッジ

- **エッジ1（session0 から Local\ は開けない）**：「やらないこと」に **サービス/タスクスケジューラのセッション0起動は非対象** を追記。
- **エッジ2（WaitAny 64 上限）**：待機コードに「配列は2要素固定（64要素上限注意）」の1行注記。
- **エッジ3（TryOpenExisting の PermissionDenied 隠蔽）**：`TryOpenExisting` を `try/catch(UnauthorizedAccessException)` で包み、権限拒否は `Trace.WriteLine` で診断可能に（本番は握り潰し継続＝終了）。
- **エッジ4（テストホストの Application.Current 誤参照）**：採用＝**`SingleInstanceManager` は WPF（Application/Dispatcher）に一切依存しない**。`StartListening(Action onActivate)` でコールバックを注入し、WPF 前面化ロジック（`BringToFront`）は `App.xaml.cs` 側に置く。テストは WPF を触らない素の `Action`（フラグ立て）を渡す。

### 依存関係の反映
- `PrivilegeService.TryRestartAsAdministrator`：致命1 の環境変数セットを追加（runas 直前に親環境へ）。戻り値で失敗を隠さない（事例「DeleteValue サイレント失敗」回避）＝セット失敗時もログのみで再起動は続行。
- `GraphicsService.cs` line 25 コメント：「Mutex を持たない」→「セッション内は単一インスタンス強制済（Mutex）。ただし same-process 複数スレッドの first-touch 競合は本サービス側ロジックの領域」へ正確化（将来の開発者が「2窓は絶対起きない」と誤解しないよう範囲を明示）。

### テストプロジェクト
- OS 往復テストは `WinKnobs.Tests`（`UseWPF=true`）内に置くが、**WPF 型に触れない**（コールバックは素の Action）。STA 不要・MTA で動く。`[Collection]` で直列化。

- **重要3（OnStartup catch が中途半端な `_single` を残す）**：採用・修正済み。catch で `_single?.Dispose()`＋`_single = null`。
- **重要4（Join(1000) タイムアウト後のハンドル破棄診断）**：採用・修正済み。`Join` の戻り値を見て未離脱なら `Trace.WriteLine`。実機/CI 高負荷で 1000ms が十分かは在席/実機確認に残す（ただし `ObjectDisposedException` は ListenLoop で正常停止扱い＝安全側）。

### 軽微
- **軽微1（引数名の将来衝突）**：コメント追記済み（将来 D&D/プロトコル拡張時はフラグを先頭で消費）。
